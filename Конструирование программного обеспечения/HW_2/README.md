# HSE-Bank - Учет финансов

## Общая идея решения

Разработана система финансового учета для банковского приложения, реализующая полный цикл работы с финансовыми данными: управление счетами, категориями, операциями, аналитика и импорт/экспорт данных.

### Реализованный функционал
- **Управление счетами**: создание, редактирование, удаление, просмотр
- **Управление категориями**: создание категорий доходов/расходов, редактирование, удаление
- **Управление операциями**: проведение операций доходов/расходов с автоматическим пересчетом баланса
- **Аналитика**:
    - Расчет разницы доходов/расходов за период
    - Группировка операций по категориям
    - Детальная статистика по операциям
- **Импорт/экспорт данных**:
    - Поддержка форматов: CSV, JSON, YAML
- **Управление данными**: автоматический пересчет баланса при операциях
- **Статистика**: измерение времени выполнения пользовательских сценариев

#### Дополнение к функциональным требованиям:
- Добавлена поддержка **кредитных счетов** с отрицательным балансом
- Реализована **расширенная аналитика** с группировкой по периодам
- Добавлена **подробная валидация** данных на уровне фабрик

##  Принципы SOLID и GRASP

### Принципы SOLID:

#### 1. **Single Responsibility Principle**
- BankAccountFacade - отвечает за работу со счетами
- CategoryFacade - отвечает за работу с категориями
- OperationFacade - отвечает за работу с операциями
- AnalyticsFacade - отвечает за аналитику
- Каждый импортер/экспортер отвечает за свой формат

#### 2. **Open-Closed Principle**
- DataImporter/DataExporter - легко добавлять новые форматы
- ICommand - легко добавлять новые команды
- IRepository - можно изменить реализацию хранения данных

#### 3. **Liskov Substitution Principle**
- Все импортеры реализуют IDataImporter и взаимозаменяемы
- Все фасады следуют контрактам своих интерфейсов
- Все команды реализуют ICommand

#### 4. **Interface Segregation Principle**
- Раздельные интерфейсы для разных фасадов
- IBankAccountFacade, ICategoryFacade, IOperationFacade, IAnalyticsFacade
- Каждый клиент зависит только от нужных ему методов

#### 5. **Dependency Inversion Principle**
- Зависимости осуществляются через конструкторы
- Использование Microsoft.Extensions.DependencyInjection
- Высокоуровневые модули не зависят от низкоуровневых

### Принципы GRASP:

#### 1. **High Cohesion**
- Services/Facades - связанная функциональность группируется вместе
- Services/Import/Export - весь импорт/экспорт в одном месте
- Utilities - вспомогательные классы для UI

#### 2. **Low Coupling**
- Минимальные зависимости между модулями
- Связь только через интерфейсы
- DI контейнер управляет зависимостями

#### 3. **Information Expert**
- OperationFacade содержит логику пересчета баланса
- AnalyticsFacade содержит логику аналитики
- Каждый фасад - эксперт в своей области

#### 4. **Creator**
- Фабрики создают доменные объекты
- ImportManager создает импортеры по расширению файла

## Паттерны GoF

#### 1. **Фабрика (Factory)**
- **Классы**: BankAccountFactory, CategoryFactory, OperationFactory
- **Важность**: Централизованное создание объектов с валидацией
- **Применение**: Используется для гарантии корректности доменных объектов и предотвращения создания объектов с невалидными данными

#### 2. **Фасад (Facade)**
- **Классы**: BankAccountFacade, CategoryFacade, OperationFacade, AnalyticsFacade
- **Важность**: Упрощение сложной системы
- **Применение**: Предоставляет простой интерфейс для работы со сложной доменной моделью

#### 3. **Декоратор (Decorator)**
- **Классы**: CommandDecorator
- **Важность**: Добавление функциональности без изменения классов
- **Применение**: Позволяет добавлять измерение времени к любым командам

#### 4. **Прокси (Proxy)**
- **Классы**: InMemoryRepository
- **Важность**: Контроль доступа к данным
- **Применение**: Реализует кэширование и управление доступом к данным

#### 5. **Адаптер (Adapter)**
- **Классы**: Все импортеры/экспортеры
- **Важность**: Совместимость интерфейсов
- **Применение**: Преобразует внешние форматы данных во внутреннюю модель

#### 6. **Команда (Command)**
- **Классы**: ICommand, CreateAccountCommand, CreateCategoryCommand, etc.
- **Важность**: Инкапсуляция запросов
- **Применение**: Позволяет параметризовать клиентов операциями и поддерживает отмену операций

#### 7. **Шаблонный метод (Template Method)**
- **Классы**: DataImporter, DataExporter
- **Важность**: Переиспользование кода
- **Применение**: Определяет общий алгоритм импорта/экспорта, позволяя подклассам переопределять отдельные шаги

#### 8. **Стратегия (Strategy)**
- **Классы**: CsvImporter, JsonImporter, YamlImporter, etc.
- **Важность**: Взаимозаменяемость алгоритмов
- **Применение**: Выбор формата импорта/экспорта во время выполнения

## Инструкция по запуску

### 1. Сборка проекта:
```bash
dotnet build
```

### 2. Запуск приложения:
```bash
dotnet run
```

### 3. Тестирование функциональности:

#### Импорт данных:
- Создайте файлы в форматах CSV, JSON или YAML
- Используйте меню "Импорт данных"
- Примеры тестовых файлов в папке TestData

#### Экспорт данных:
- Используйте меню "Экспорт данных"
- Укажите путь с нужным расширением (.csv, .json, .yaml)

#### Демонстрационные данные:
- При первом запуске автоматически создаются демо-данные
- Можно удалить и создать заново через соответствующие меню
